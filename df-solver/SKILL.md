---
name: df-solver
description: 按 task.md 的本次任务并行推进实现，依据每项标注的方式分派给主 Agent、subagent 或后台任务；完成后把本次变更合并进全局 spec.md 与 design.md，回填 task.md 状态与 validation.md 遗留，并出简报等用户确认。
---

df-solver 做两件事：把 `task.md` 里的任务跑完，然后把这次改动的结果**合并进全局基线**。不新增需求、不扩范围、不改 delta 正文。

## 变量

| 变量 | 用途 | 说明 |
|---|---|---|
| `df_proj_dir` | 工程根 | 重要!!，禁止丢弃 |
| `df_us_id` | 本次变更编号 | 重要!!，禁止丢弃 |
| `df_spec_dir` | `{df_proj_dir}/codespec/specs`，基线落点 | - |
| `df_change_dir` | `{df_proj_dir}/codespec/changes/{df_us_id}` | - |

变量缺失时先跑一次 `df-env` 补齐。

## 语言规范（动手前必读）

`references/` 按语言给出代码规范与坏味道，动手前按任务的 `涉及文件` 取对应文档：

| 扩展名 | 文档 |
|---|---|
| `.c` `.h` | `references/c.md` |
| `.cc` `.cpp` `.cxx` `.hpp` | `references/cpp.md` |
| `.java` | `references/java.md` |
| `.py` `.pyi` | `references/python.md` |
| `.go` | `references/go.md` |
| `.rs` | `references/rust.md` |
| `.js` `.jsx` `.mjs` `.cjs` | `references/js.md` |
| `.ts` `.tsx` | `references/ts.md` |

- 一个任务涉及多种语言就读多份；`references/README.md` 是索引
- **派 subagent 时把文档路径写进它的简报**，让它自己读，不靠转述
- 主 Agent 自己动手的任务同样受这些约束
- 项目自带的 lint / format 配置优先；文档只补项目没约束到的部分
- 本次改动**直接涉及**的代码命中坏味道，就在同一任务内改掉；范围之外的只记进简报，不顺手重构

## 步骤

### 1. 读输入并守门

| 文件 | 用途 | 缺失或异常时 |
|---|---|---|
| `{df_change_dir}/task.md` | 本次任务清单 | **停手**：清单缺失无法执行 |
| `{df_change_dir}/scope.md` | 执行边界：可改白名单 / 明确不动 / 越界处置 | **停手**：边界缺失无法判断越界 |
| `{df_change_dir}/delta-spec.md`、`delta-design.md` | 验收口径、设计落点、基线合并依据 | **停手**：缺验收口径或设计落点，先补齐 |
| `{df_change_dir}/validation.md` | 遗留项；是否还有未修的严重问题 | 缺失 → 停手；仍有"待用户决策"的严重项 → 停手交用户定 |
| 基线 spec（`specs/spec.md` 或 `specs/<capability>/spec.md`）、`design.md` | 基线，本次要合并进去 | 一份都没有 → 停手：基线尚未建立 |

再确认 `task.md` 只含本次 US 的任务——出现别的变更编号，一律不执行并指出。

### 2. 询问测试模式

动代码之前问一次，二选一，答案写进 `task.md` 的 `## 测试策略`：

```js
AskUserQuestion({
  "questions": [
    {
      "header": "测试模式（也可直接输入你的要求）",
      "question": "本次实现是否走 TDD——先写失败测试，再写刚好能过的实现？",
      "options": [
        {"label": "TDD (Recommended)", "description": "先红后绿、一次一个切片；回归由测试兜住"},
        {"label": "常规", "description": "先实现后补测试；只在该任务的验收命令里跑测试"}
      ],
      "multiSelect": false
    }
  ]
})
```

用户没回答就重问，**不许默认选一个继续**。

选 TDD 时，实现过程按 `df-tdd` 的规则执行——红→绿循环、一次一个切片、测试只写在和用户确认过的 seam、验行为不验实现、期望值必须来自独立事实源。

`df-tdd` 另外列了「什么时候不适合 TDD」（纯配置、探索性原型、一次性脚本），动每个任务前照它判一次，别硬套。

重构不属于这个循环，留给评审阶段。

选定后回填 `task.md` 的 `## 测试策略`：写"TDD"或"常规"，TDD 再补一句"每任务至少先有失败测试，验收命令包含测试命令"。**只回填这一节，不动任务列表。**

### 3. 组波次

- 按 `依赖` 列建 DAG，无依赖的任务进同一波
- `涉及文件` 有重叠的任务**不许同波**，即使没有显式依赖——它们会互相踩
- 先把波次表讲出来：第 1 波 = {T1, T3}，第 2 波 = {T2} …

### 4. 按方式分派

| 方式 | 怎么跑 |
|---|---|
| `主 Agent` | 当前会话自己动手，不派子代理；适合需要边做边与用户确认的收尾与整合任务 |
| `subagent` | 一个任务一个子代理，边界写死为它那行的`涉及文件`；回执必须带证据 |
| `后台` | 长命令、构建、批量生成或重命名交给后台任务；完成信号必须是可判定的（退出码 / 产物存在） |

同一波里三种方式可以混用：subagent 与后台并行跑，主 Agent 同时干自己那份。

分派纪律：

- 子代理**只许改**它那行列出的文件，越界即失败
- 子代理的回执要有：改了哪些文件、跑了什么命令、结果如何
- **先对边界再动手**：每个任务动手前，把它要改的每个文件对一遍 `scope.md` 的白名单；命中"明确不动"或落在白名单外，一律**停手**，按越界话术报给用户（需要改 X 因为 Y 对应 Z 需求），拿到确认才扩范围
- 单个任务重试上限 2 次；仍失败标 `阻塞`，在简报里点名，不静默吞掉
- 主 Agent 的任务不许转派给子代理来"并行化"——方式由 `task.md` 定，擅自改方式等于跳过用户已确认的拆分

### 5. 每波收口

一波结束后，逐条核对 `task.md` 的完成判据，**证据先行**：

- **不许凭"看起来对了"置 `完成`**：必须真的跑过该任务的验收命令，并记下命令与关键输出；没跑或跑不了，状态只能是 `进行中`
- 满足 → 状态置 `完成`，并把验收命令记进本波记录
- 不满足 → 按下面的调试纪律处理；超过重试上限置 `阻塞`，写清卡在哪
- 有阻塞时先问用户：跳过继续，还是停下来处理

**失败时的调试纪律**（禁止边猜边改）：

1. **先复现**：给出可重复触发的最小命令或输入，没有复现不算定位
2. **再定因**：说清"为什么失败"；拿不准就加日志或断言去证，不靠猜
3. **一次只改一个变量**，改完立刻重跑验收命令
4. **同一原因连续两次没修好** → 停下标 `阻塞`，把已排除的可能性列出来交给用户，不继续试错

### 6. 合并进基线

任务跑完后，把本次变更合并进 `{df_spec_dir}/spec.md` 与 `design.md`——不做这一步，基线与代码就会脱节。

**合并依据**：`delta-spec.md` 的四类差异 + `delta-design.md` 的 `## Changes` 与 `## Baseline Diff` + 实际代码改动的结果。

`spec.md` 的合并规则：

| delta 里的类别 | 动作 |
|---|---|
| `ADDED` | 新增 `### Requirement:`，至少带一个 `#### Scenario:` |
| `MODIFIED` | 就地改对应条目，保留其章节位置 |
| `REMOVED` | 删掉该条目整节，含其场景 |
| `RENAMED` | 只改标题，正文与场景不动 |

基线 spec 可能有多份文件：按能力拆分时，`<capability>/<需求名>` 定位到 `{df_spec_dir}/<capability>/spec.md`；单文件布局直接改 `spec.md`。定位不到就报错，不许在错误的文件里改。

`design.md` 按 `## Baseline Diff` 更新对应章节：`架构总览`、`组件与依赖`、`关键流程时序` 的图按**实际实现**重画（节点名实读代码确认），`Decisions` 追加本次决策与理由，`Risks / Trade-offs` 更新。

决策已有 ADR 时，`## Decisions` 写链接加一句摘要（如 `见 docs/adr/0007-x.md`），**不复述 ADR 全文**——ADR 是决策的事实源，design.md 只做索引。发现两者矛盾时以 ADR 为准，并在简报点名。

三条硬约束：

- **以实现为准**：代码实际行为与 delta 不一致时，基线写实际行为，并把差异写进简报与 `validation.md` 的遗留。不许照抄 delta 把偏差盖住。
- **合并必须幂等**：`ADDED` 的条目若基线里已有同名需求，就地更新而不是再追加一条；同一 US 因评审返工而重跑合并时，不得出现重复章节。
- **现在时**：合并后不允许出现"将要/改为"或 `> 待实现：`；基线描述的是已经成立的事实。
- **只改这两份**：基线可以由本 skill 更新，delta 正文一律不动。

合并后必跑一次结构校验（脚本随本 skill 一起分发，路径 `scripts/check.py`，找不到就跳过并在简报里说明）：

```bash
python "<本 skill 目录>/scripts/check.py" --proj "{df_proj_dir}" --us "{df_us_id}" --baseline-only
```

有 `严重` 项就修到 0 再出简报——基线是唯一被反复覆盖的文件，合并完不复检等于没护栏。

### 7. 回填其他文档

- `task.md`：只更新 `状态` 列（`待办` / `进行中` / `完成` / `阻塞`），**不改任务正文**
- `validation.md`：`## 遗留` 里标着"实现后确认"的条目给出结论；实现与 delta 的分叉记在这里；仍无解的原样留着

### 8. 简报与确认

收尾前输出一段简报（不超过 8 行），然后在同一条消息里提一题。简报至少包含：

- 完成 `<N>/<M>` 个任务，阻塞 `<K>` 个（点名）
- 分派构成：主 Agent `<a>` / subagent `<b>` / 后台 `<c>`
- 关键改动落在哪些模块
- **验证证据**：每个 `完成` 的任务跑了哪条验收命令、结果如何（一条一行，不许写"已验证"了事）
- **测试模式**：TDD 还是常规；TDD 时说明新增了几个测试、覆盖哪几个 seam、是否都先红后绿
- **基线合并结果**：`spec.md` 增/改/删/改名各几条；`design.md` 更新了哪几节；与 delta 不一致之处（没有就写"无"）
- `task.md` 状态与 `validation.md` 遗留的结论
- 未决项或假设（没有就写"无"）

```js
AskUserQuestion({
  "questions": [
    {
      "header": "验收（要改什么就直接输入）",
      "question": "简报如上，符合你的要求吗？不符合就直接输入要改的地方。",
      "options": [
        {"label": "符合", "description": "本次实现与基线定稿，`task.md` 与 `validation.md` 保持当前状态"}
      ],
      "multiSelect": false
    }
  ]
})
```

- 只有两类回答：`符合`，或用户直接输入修改意见
- 用户输入 → 按意见改 → 重新出简报 → 再问一次
- **迭代上限 3 轮**；到顶仍未确认，列出未达成项并停手，不再自行修改

## 边界

- **只做 `task.md` 里的本次任务，且只在 `scope.md` 的白名单内**：不新增需求、不顺手重构、不清理无关代码。
- **越界即停**：白名单外的文件即使"改了更好"也不许动，必须先报告并拿到确认。
- **只更新基线与回填**：允许写 `spec.md`、`design.md`（合并本次结果）、`task.md` 状态、`validation.md` 遗留；`delta-spec.md` / `delta-design.md` 正文不动。
- **不改任务拆分**：方式与边界由已确认的 `task.md` 定；唯一允许的回填是 `## 测试策略` 一节。
- **不合并架构文档**：`docs/arch_{US}.md` 并入 `docs/arch.md` 属于收尾环节；本 skill 也不写 `README.md`。
- **不推进 `df_stage`**。
- **提问只用 AskUserQuestion**。
- **宿主没有 AskUserQuestion 时**：退回编号列表提问，不跳过提问。
